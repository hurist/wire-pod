# Wire-Pod 二次开发讨论备忘录

> 整理日期：2026-07-06
> 主题：基于 Wire-Pod 框架的二次开发定位、能力边界与 Vector 机器人屏幕能力

---

## 1. 总体判断

Wire-Pod 适合被二次开发成一个**本地机器人 AI / 自动化中枢**。

它的核心价值不是简单远程控制 Vector，而是完整替代官方云服务，让服务端接管语音识别、意图路由、AI 对话、脚本执行、插件扩展、机器人动作反馈等能力。

一个更准确的产品定位是：

```
Wire-Pod 是本地 AI / 自动化中枢，
Vector 是这个中枢的机器人化前端。
```

---

## 2. Vector 与服务端的分工

在这套架构下，Vector 更像一个“具身前端”，主要负责输入、输出和情绪化反馈；真正的任务核心主要在服务端执行。

### 2.1 Vector 端主要负责

- 采集用户语音
- 提供摄像头输入
- 播放语音
- 播放表情和动画
- 移动、转头、抬升降臂
- 显示简单图片或状态
- 作为用户面前的实体交互终端

### 2.2 Wire-Pod 服务端主要负责

- STT 语音识别
- 意图匹配
- LLM 对话
- 对话记忆
- 自定义意图
- Lua 脚本执行
- Go 插件加载
- 外部 HTTP API 调用
- 智能家居、MQTT、Home Assistant 等系统联动
- 机器人认证、配置、JDocs、Token 管理
- Web 管理后台

### 2.3 典型交互链路

```
用户对 Vector 说话
    -> Vector 上传音频到 Wire-Pod
    -> Wire-Pod 做 STT 识别
    -> Wire-Pod 做意图匹配或调用 LLM
    -> Wire-Pod 执行插件、脚本或外部自动化
    -> Wire-Pod 让 Vector 说话、播放动画、移动或显示图片
```

因此，二次开发时不应把复杂逻辑塞进机器人端，而应把服务端能力做强，再让 Vector 负责自然交互和可爱的物理反馈。

## 3. 当前框架已经支持的扩展能力

### 3.1 语音与 AI 能力

- 多 STT 引擎：Vosk、Whisper API、whisper.cpp、Coqui、Leopard、Houndify 等
- LLM 接入：OpenAI、Together、自定义 OpenAI-compatible 接口
- 流式 AI 回复
- 按机器人 ESN 保存对话记忆
- 通过特殊命令让 LLM 触发机器人动作

### 3.2 意图和脚本能力

- 自定义语音意图
- 基于 JSON 的 utterance 配置
- Lua 脚本执行
- 外部程序执行
- Go `.so` 插件扩展
- 内置意图、插件意图、自定义意图和 LLM fallback 的组合路由

### 3.3 机器人控制能力

- 说话
- 播放动画
- 头部运动
- 升降臂运动
- 轮子运动
- 屏幕显示图片
- 摄像头相关能力
- 设置眼睛颜色和其他机器人配置
- 通过 SDK App 做远程控制

### 3.4 Web 和配置能力

- Web 管理后台
- 配置 API
- 日志查看
- 自定义意图管理
- 多机器人信息存储
- 本地 JSON 配置持久化

## 4. 适合做的二次开发方向

### 4.1 低成本方向

- 中文语音命令包
- 家庭常用指令，例如开灯、关灯、查天气、倒计时
- Lua 行为脚本库
- Webhook 联动
- 个性化 Prompt
- 简单状态播报
- 多机器人命名和分组
- Web 后台界面优化

### 4.2 中等成本方向

- 接入 Home Assistant
- 接入 MQTT
- 接入国内 LLM，例如通义、豆包、智谱、DeepSeek、Kimi 等
- 接入中文 STT / TTS
- 插件管理页面
- 技能系统，例如天气、日历、提醒、备忘录、待办事项
- 长期记忆，例如 SQLite、向量库、RAG
- 多机器人协作

### 4.3 深度改造方向

- 将关键词意图路由升级为 LLM function calling
- 建立完整 Agent 框架
- 接入视觉模型，让 Vector 摄像头用于识别物体、人或环境
- 本地离线 AI：本地 STT + 本地 LLM + 本地 TTS
- 支持更多机器人或自研硬件接入
- 拆分服务端模块，例如语音服务、LLM 服务、控制服务、配置服务

## 5. 推荐产品化方向

### 5.1 Vector 中文智能管家

让 Vector 以中文完成语音问答、智能家居控制、日程提醒、天气播报等家庭助手任务。

### 5.2 桌面 AI 伙伴

重点强化 LLM 对话、人格设定、记忆、动画反馈和屏幕表情，让 Vector 成为一个有存在感的桌面 AI 伙伴。

### 5.3 家庭自动化语音入口

将 Wire-Pod 连接 Home Assistant / MQTT / Webhook，让 Vector 成为智能家居的实体语音前端。

### 5.4 机器人技能商店

把 Lua 脚本和 Go 插件封装为可安装技能，在 Web 后台完成安装、配置、启停和日志查看。

### 5.5 本地隐私版 AI 机器人

使用本地 STT、本地 LLM、本地 TTS，尽量减少对外部云服务的依赖，适合 NAS、小主机、家庭服务器部署。

## 6. Vector 屏幕能力

Vector 的屏幕主要是脸部显示屏，不是手机或网页那种通用显示屏。它更适合做表情、图标和极简状态提示。

### 6.1 适合显示的内容

- 默认眼睛和表情动画
- 固件内置动画画面
- 自定义图片
- 图标
- 天气状态
- 简单表情
- 二维码
- 状态图
- 小型像素图
- 简短文字渲染成的图片
- 简单进度条或倒计时
- 颜色和图案类状态反馈

### 6.2 可以通过服务端实现的方式

仓库中的 Lua 脚本能力已经暴露了：

```lua
showImage(filePath, durationMs)
```

其底层会把图片转换为 Vector 脸屏可显示的 RGB 位图，并调用机器人 SDK 的 `DisplayFaceImageRGB` 相关能力。

如果要显示文字，推荐服务端先把文字渲染成图片，再显示到屏幕上。适合短词或短状态，例如：

```text
OK
25 C
门开了
会议中
完成
```

### 6.3 不适合的内容

- 长文本
- 多行列表
- 复杂仪表盘
- 网页
- 视频播放
- 信息密集型 UI

屏幕定位更接近“表情和提示牌”，不是完整信息显示器。

## 7. 当前框架的主要边界

- Go 核心服务不支持热重载，修改后需要重新编译。
- 部分 STT 引擎是通过不同 `cmd/` 入口编译绑定，不是完全运行时插件化。
- 全局状态较多，深度改造时需要注意并发安全。
- Go `.so` 插件跨平台兼容性有限，在 Linux / Docker 下更稳。
- Web UI 是原生 HTML / JS / CSS，简单直接，但复杂后台可能需要重构前端组织方式。
- Vector 屏幕分辨率和刷新能力有限，适合极简状态显示，不适合复杂 UI。

---

## 8. 建议的下一步开发顺序

如果目标是做一个面向中文和家庭场景的实用版本，推荐按以下顺序推进：

1. 先完善中文 STT / TTS / LLM 接入。
2. 增加 Home Assistant 或 MQTT 集成。
3. 建立统一的工具调用接口，让 LLM 能安全调用插件和自动化能力。
4. 增加长期记忆和用户偏好存储。
5. 扩展 Lua / 插件管理后台。
6. 为 Vector 屏幕建立一套小型状态卡片渲染能力。
7. 最后再考虑 Agent、多机器人协作和本地离线模型。

---

## 9. 一句话结论

Wire-Pod 的二次开发重点应放在服务端：把服务端做成 AI、自动化、记忆和工具调用的大脑；Vector 负责听、说、看、动和显示简单反馈。这样最符合现有架构，也最能发挥 Vector 作为实体机器人前端的价值。
